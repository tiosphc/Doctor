# ERP Phase 10 — Dealer Excel Order Import

## Architecture and scope

Phase 9 `DealerQuickOrderService` already owns active Dealer membership and Tier resolution, Dealer SKU pricing and MOQ, default sales Warehouse, stock review, fingerprint checks, and submission through `SalesOrderService` and `InventoryReservationService`. Phase 10 adds an XLSX input adapter: upload → parse → normalize → group → preview → revalidate → confirm. The parser never inserts Sales Orders. Each intended order calls the same `DealerQuickOrderService::review` and `::submit` methods used by Quick Order. It is confirmed and reserved through the existing Sales Order core. The Product pricing CSV helper is a separate Admin pricing workflow and is not reused here.

This is self-service for one route-selected, active Dealer Account and authenticated active member. There is no Admin multi-Dealer import, Retail import, Dealer Cart, payment, credit/debt, automatic Tier calculation, promotion, return/refund, warehouse transfer, procurement, lot/batch/FEFO, or clinic material workflow.

## Workbook and file handling

The downloadable `.xlsx` has `Orders` and `Instructions` sheets. `Orders` has exactly these ten headers, in this order: `SKU`, `Customer Name`, `Phone`, `Email`, `Street`, `City`, `State`, `Country`, `Zip Code`, `Quantity`. Each row is one SKU/line item; the SKU alone identifies its variant, so Size and Style are forbidden. The user does not enter an order/group/Dealer ID, status, price, Tier, MOQ, Warehouse, total, currency or payment/fulfillment field. A legacy optional `Voucher Code` column remains accepted for existing promotion imports but is absent from the simple template. Unknown and duplicate headers are rejected. Phone, zip code and SKU must be Excel text cells so leading zeroes survive. Formula cells, macro/external-link parts, unsafe archive paths, malformed XML and unsupported files are rejected. `.xls` and `.xlsm` are unsupported. The project example workbook is `docs/dealer_orders_two_recipients.xlsx`.

The project has no installed XLSX library and the local PHP runtime lacks `ext-zip`. `DealerOrderImportWorkbook` uses PHP's built-in `PharData` ZIP support and DOM XML parser without a dependency change. Uploaded files use a random name on the private Laravel `local` disk, then are deleted in `finally` after parsing, including parser failure. Only filename, byte size, SHA-256 hash and normalized rows/results persist. Neither API nor audit log exposes local paths or recipient details. Configuration in `config/dealer_order_import.php` sets 5 MB compressed, 30 MB uncompressed, 1000 data rows, 100 intended orders and 50 lines per order. The ZIP entry and worksheet-row guard further constrain parsing. Production must enable `phar`, `zlib` and `dom` PHP extensions and writable private local temporary storage.

## Data and validation

Migration `2026_09_25_084440_create_dealer_order_imports.php` adds nullable `sales_orders.external_reference` and normalized comparison column with a unique `(dealer_account_id, external_reference_normalized)` index. Quick Orders may leave both null. `dealer_order_imports` tracks owner, file metadata, counts, lifecycle, fingerprint and confirmation key. Child row records retain Excel row number, normalized SKU, quantity, recipient snapshot, resolved variant and errors. Group records retain one intended order, preview, review fingerprint, status/error and optional resulting Sales Order. Internally generated normalized group references preserve retry/idempotency protection, while resulting Sales Orders leave `external_reference` null. Foreign keys and unique import-row, import-group and order-ref constraints protect the relationships. This simplification requires no new migration and does not reset existing data.

Rows are grouped by normalized phone plus `Street`, `City`, `State`, `Country` and `Zip Code`; surrounding/repeated whitespace and address letter case do not split an order. Different phone or shipping address produces a different order, even when the name matches. Groups are labeled `GROUP-001`, `GROUP-002`, etc. in first-seen order. Repeated SKU rows within one group have their positive whole-unit quantities summed into one Sales Order Item. Conflicting name/email within a group is shown as a row-level recipient error rather than silently choosing one value. SKU uses the project's `Sku::normalize`; phone formatting is reduced to digits and email is trimmed/lowercased. The importer rejects missing required fields, non-integer/zero quantity, missing/non-sellable SKU and conflicting promotion values. `Zip Code` is optional under the existing shipping rule; Email is optional but must be valid when supplied. Recipients are order snapshots; no User or Customer is created. Every group resolves current Dealer Account/Tier/override, Dealer price and MOQ, and the default sales Warehouse through the shared Quick Order review. There is no Retail price fallback. Preview checks each SKU and total demand across the whole file against available stock, but creates no order, item, reservation or stock movement.

The import fingerprint covers Account and each group's internal reference, recipient, current Quick Order review fingerprint, errors and linked order. Revalidation refreshes commercial facts. Confirm revalidates before the first order and rejects changed/invalid previews. Each group is separately transactional and invokes shared Quick Order submit, which rechecks Account/membership, Tier, price, MOQ, Warehouse and stock under locks. Successfully created groups remain linked on partial completion; failed groups retain an error and can be revalidated and retried. A deterministic per-group operation key, import confirmation key/payload check and internally generated reference uniqueness prevent duplicate orders. A completed file hash for the same Account is rejected on reupload. The shared Sales Order core retains Dealer/Tier/price/MOQ/recipient snapshots, Wallet settlement and reservation; later Admin fulfillment/cancellation still uses the existing core. Import upload, confirmation and completion have PII-free audit entries.

## API and UI

All routes require Sanctum authentication and active Account context:

| Method | Route | Purpose |
| --- | --- | --- |
| GET | `/api/dealer/accounts/{dealer}/order-imports/template` | Download XLSX |
| GET | `/api/dealer/accounts/{dealer}/order-imports` | Uploader's history |
| POST | `/api/dealer/accounts/{dealer}/order-imports` | Upload and preview |
| GET | `/api/dealer/accounts/{dealer}/order-imports/{import}` | Uploader's detail |
| POST | `/api/dealer/accounts/{dealer}/order-imports/{import}/revalidate` | Refresh preview |
| POST | `/api/dealer/accounts/{dealer}/order-imports/{import}/confirm` | Confirm with UUID key and fingerprint |

The responsive `/dealer/import-orders` page uses the authenticated primary Dealer Account, downloads the ten-column template, uploads `.xlsx`, previews `GROUP-###` with customer, address, distinct SKU count, total quantity, products, pricing and row/field errors, revalidates, confirms with a dialog, and links created orders/import history. Admin Sales Orders can filter by `dealer_excel`; new imports have no customer-entered external reference. APIs reject client-supplied Tier, price, Warehouse, totals and Account IDs.

This version parses an XLSX into a bounded DOM tree, so the configured file/expanded-size/row limits are operational constraints. It supports only canonical `.xlsx` templates and multi-order mode. Import history is limited to the uploader, while the resulting Sales Order remains visible to authorized Account coworkers. A failed group may need an explicit revalidation and a fresh confirmation key after a partial run. No raw workbook is retained for later download.
